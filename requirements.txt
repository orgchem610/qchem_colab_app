# 「今後最新版がリリースされても動作が変わらないように」という要望に対して、
# 本プロジェクトでは2段構えの対策を取っています。
#
# 【対策 1: Colab自体のランタイムを固定する】(Python本体・numpy等)
#   Google Colabには「過去のランタイムバージョンに固定する」公式機能があります
#   (ノートブック上部メニュー「ランタイム」→「ランタイムのタイプを変更」内の
#   「Runtime version」プルダウン)。固定した時点のUbuntu/Python/numpyの
#   組み合わせが最大1年間re-appearする仕組みです。
#   本プロジェクトの開発時点(2026年9月)で選べた最新スナップショットは
#   「2026.07」(Ubuntu 22.04.5 LTS / Python 3.12.13 / numpy 2.0.2)でした。
#   ColabApp.ipynb を配布する際は、このバージョンをノートブックのメタデータ
#   および下記の運用ルールとして固定することを推奨します。
#   参考: https://research.google.com/colaboratory/runtime-version-faq.html
#
# 【対策 2: このファイルでpipパッケージを固定する】
#   下記のバージョンは、開発時点(2026年9月)でPyPI上に存在が確認できた
#   バージョンです。将来にわたって「絶対にこの通りに動く」ことを保証する
#   ものではないため、本プロジェクトでは以下の運用を推奨します。
#
#     1. 初めてColab上でSetup Sectionを実行し、正常にインストールが
#        完了したら、そのセルの最後で自動的に
#            !pip freeze > requirements-lock.txt
#        を実行し、実際にインストールされた「動作確認済み一式」を
#        書き出します(ColabApp.ipynb に組み込み済み)。
#     2. requirements-lock.txt をGitにコミットし、
#        「このバージョンで動作確認済み」というタグ(例: v0.1.0)を打つ。
#     3. 以後、同じ結果を再現したい場合は、下記のrequirements.txtではなく
#        requirements-lock.txt からインストールする
#        (!pip install -r requirements-lock.txt)。
#
#   つまり、requirements.txt は「最初の一回を動かすためのベストエフォートな
#   目安」、requirements-lock.txt は「実際に動作確認できた正確な記録」という
#   役割分担です。バージョン管理の設計については README.md / CHANGELOG.md も
#   あわせてご覧ください。
#
# 【GPU4PySCFについて】(あえて緩め・未確定にしている)
#   GPU4PySCFはColab側のCUDAドライババージョンに強く依存し、対応バージョンが
#   pyscf本体よりも頻繁に変わるため、ここでは厳密な固定を避けています。
#   ColabApp.ipynb のSetup Section内で、Colab提供のCUDAバージョンを検知して
#   gpu4pyscf-cuda11x / gpu4pyscf-cuda12x のいずれかを都度選択インストールし、
#   万一インストールに失敗してもCPU実行にフォールバックする設計です
#   (qcapp/engine.py 参照)。
# =============================================================================
